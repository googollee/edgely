## 背景与问题

滑雪爱好者（尤其双板）很难量化评估自己的技术细节——刃角够不够、左右转弯是否对称、重心转移的时机——肉眼和录像只能看个大概，且录像分析门槛高。市面上有类似方案（如 Carv）但价格高、生态封闭。目标是用现成的姿态传感器（IMU），自己搭一套低成本、可扩展的采集+分析方案。

MVP 阶段先解决最基础也最容易被低估的问题：**数据能不能稳定、完整地采到**。技术分析算法（转弯识别、刃角、对称性等）依赖真实滑雪数据才能设计，因此本阶段不做算法实现，只把数据采集闭环打通。

## 目标（Goals）

- 验证 1~2 个传感器的蓝牙数据采集在真实滑雪场景下的稳定性（连接、掉线检测、续航）。
- 验证 GPS、电量等辅助数据流能否与 IMU 数据同步采集、完整存储。
- 产出一个能记录一趟滑行、并可通过历史记录列表进入时间轴回放+3D 姿态查看数据是否正常的最小闭环，为后续设计分析算法积累真实数据。

## 非目标（Non-goals）

- 转弯分段算法
- 指标计算（刃角、对称性得分等技术分析）
- 实时反馈（震动/语音提示）
- 云端账号体系、多用户、社交分享
- Android 版本
- 单板滑雪或其他运动场景
- 低温环境下的任何缓解措施（不做处理，作为已知风险接受，不代表不会出问题）
- 跨 session 的指标对比（如趋势图、并排比较）——历史记录列表浏览属于 MVP 范围，见 F7

## 目标用户与场景

- 用户画像：开发者本人及愿意帮忙测试的滑雪朋友，非公开发布，用于验证技术可行性。
- 核心使用场景（用户故事）：
  - 作为滑雪者，我想连接 1 个或 2 个传感器并完成一次校准动作（无论 1 个还是 2 个，App 都能自动识别每个传感器对应左脚还是右脚），以便正确区分数据来源，而不需要额外的绑定操作或自己判断左右脚。
  - 作为滑雪者，我想用固定的 50Hz 采样率录制，不需要在录制前做配置。
  - 作为滑雪者，我想在起始界面进入历史记录列表，选择任意一趟（包括刚录完的）查看时间轴和 3D 姿态回放，以便判断这次采集是否正常、数据是否可用。

## 功能需求

### F1：传感器连接

- 需求描述：App 扫描并列出可用的姿态传感器（只列出已有设备支持的设备，没有任何设备支持时提示"没有可用的设备支持"），用户从列表中勾选要使用的传感器，可以选择 1 个或 2 个。连接阶段不区分左右身份，左右身份判定交给 F2 自动完成（1 个或 2 个传感器都自动判定，不需要用户手动指定）。
- 验收标准：用户勾选的传感器都能成功建立 BLE 连接并开始接收数据流；至少勾选 1 个才能进入下一步。已连接的传感器意外断开后，App 自动尝试重新连接（校准、录制期间都一样），不需要用户操作。

### F2：功能性方向校准（含左右身份判定）

- 需求描述：连接成功后进入校准阶段，App 自动判定每个传感器装在哪只脚上，并算出它在传感器坐标系下的"前 / 左 / 下"参考系。**无论连接了 1 个还是 2 个传感器，都引导用户完成同一套四步动作**，不需要手动选择左右脚，也不需要侧向迈步。每一步由用户完成动作后**手动点击确认**：
  1. **抬起左脚，放下，站稳 → 确认**
  2. **抬起右脚，放下，站稳 → 确认**
  3. **双脚并拢自然站立、雪靴放平，站稳 → 确认**
  4. **从并拢开始，左脚向前迈一步，右脚跟上并拢 → 确认**（不要求严格，从并拢开始、到并拢结束即可）

  - **指令要求**：每一步动作**前后都要各停顿一次**（站稳后再开始，做完停稳后再点确认）；迈步要**沿脚尖方向直着迈**。两条都是算法的硬性前提，指令文案必须明确提示（原因见 ADR-0012）。
  - **时限**：每一步 10 秒，从上一步点击确认算起（第 1 步从进入校准阶段起算），覆盖看指令、调整站位、动作、停稳、点击的全过程；UI 明确显示倒计时。用户应当在开始校准前就穿戴就绪。
  - **失败处理**：任何一项判定没通过，都是校准失败，整个流程从第 1 步重来，不做局部重试。提示只细分用户能照着调整的两种情况——「动作太慢」（超时）、「动作幅度太小」——其余统一提示「校准失败，请重新开始」。
  - **留档**：每次校准尝试（含失败）的过程数据都落盘保存，不面向用户展示，用于分析判定结果、调整判定参数。

  身份判定、参考系计算、各项判定条件见 **ADR-0012**。这些是窗口内的数值比较与计算，不属于 MVP 排除范围的"分析算法"。

- 验收标准：无论 1 个还是 2 个传感器，用户都走同一套四步流程且四步都要做完，全程不需要手动选择左右脚、不需要侧向迈步；每个传感器的身份（左/右）和参考系（"前/下/左右"三轴）都被正确判定并随 session 存入 `meta.json`；任何一项判定没通过时，App 给出对应提示并整体重置回第 1 步；每次校准尝试（含失败）都在 `Calibrations/` 下留下可供分析的记录。**注**：F5 的展示会应用这个参考系，用于对齐鞋形模型的脚尖/鞋底朝向；实时倾斜程度另外由加速度计数据驱动，具体方式见 ADR-0005。
- 备注：传感器固定安装在雪靴上（见 F3），随脚一起移动，"抬脚""迈步"动作天然符合直觉；每次安装的朝向都不一样，所以才需要这一步校准。

### F3：录制配置与执行

- 需求描述：传感器固定安装在雪靴上（不支持选择安装位置）。采样率固定为 **50Hz**，不提供选择（校准的数值积分依赖采样密度，见 ADR-0012；丢帧修正参数只在 50Hz 上实测，见 ADR-0014），作为本次 session 的元数据随原始数据一起存储。
  点击"开始"后进入连续录制状态：已连接的每个传感器（1 个或 2 个）数据持续接收、打时间戳、增量写入本地文件，这段时间内不做实时分段。点击"结束"停止录制后返回起始界面（不直接进入回放，见 F5/F7），供用户开始下一趟录制或进入历史记录查看本趟数据。
  同时记录开始、结束时刻的电量（已连接的每个传感器、手机），录制过程中每分钟自动记录一次电量快照。
- 验收标准：
  - session 存储数据包含采样率元数据、绑定位置固定常量"雪靴"、本次使用的传感器数量（1 或 2）、以及实际生成的数据文件名列表，均写入 `meta.json`。
  - 电量时间序列至少包含开始点、结束点、每分钟中间快照点，每个快照含已连接传感器的电量与手机电量。
  - 采样率固定 50Hz，一次 session 内也不支持中途增减传感器。
  - 录制过程中 App 被系统挂起或蓝牙短暂断开重连后，已录制数据不丢失（增量写盘，非结束时才落盘）。

### F4：断线检测与标记

- 需求描述：录制过程中若某个传感器**连续 2 秒未收到任何数据包**，判定为断线，App 需要感知并在数据中标记缺口时间段，而不是静默丢数据/用旧值填充；重新收到数据后自动视为重连，缺口结束。
- 验收标准：复盘时能看到"此时间段数据缺失"的提示；断线阈值取 2 秒，现场测试后可按实际情况调整。

### F5：时间轴回放 + 3D 姿态渲染

- 需求描述：从历史记录列表选中某个 session 后（见 F7，回放页唯一入口），展示一个可拖动的时间轴；拖动到任意时间点时，实时渲染当前时刻已连接传感器（1 个或 2 个）对应的姿态——用一个简化的、能区分脚尖/鞋底朝向的鞋形几何体表示（不是精细雪靴/雪板模型），朝向按 F2 校准得到的参考系对齐，倾斜程度由原始加速度计数据驱动（不含偏航，具体方案见 ADR-0005）。退出回放页返回历史记录列表（不是起始界面）。
- 验收标准：拖动时间轴时姿态渲染跟手流畅；能看到本次实际使用的每只脚的姿态，未使用的一侧不展示；能直观分辨模型的脚尖/鞋底朝向；下方向在回放全程与真实重力方向保持一致；退出后回到历史记录列表。
- 技术备注：渲染引擎采用 SceneKit（见 ADR-0002）；姿态计算方式见 ADR-0005。

### F6：GPS 轨迹记录

- 需求描述：录制期间，App 通过手机 GPS 同步记录位置轨迹（经纬度、海拔、速度、时间戳），采样频率约 1Hz，作为独立数据流随 session 一起存储。定位权限采用简单流程：App 启动时按需申请，遵循 iOS 标准系统弹窗，不做额外引导设计。
- 验收标准：session 数据包含 GPS 轨迹序列；App 切到后台时定位记录不中断。

### F7：历史记录列表

- 需求描述：从起始界面（F1 连接页）提供入口进入历史记录列表，列出 `Sessions/` 目录下所有已保存的 session，按时间倒序排列（最新的在最上面）。每行只显示 session id，不展示时长、传感器数量等额外信息。点击某一行，进入 F5 回放页，回放对应 session 的数据。历史记录列表本身也提供返回起始界面的入口。
- 验收标准：列表能展示磁盘上实际存在的所有 session；点击任意一行都能正确进入该 session 的回放页、数据正确加载；可以返回起始界面；不提供跨 session 的对比或统计视图（见非目标）。

## 数据存储设计

原始数据使用 JSON，**每个 session 一个目录**，内含多个 JSON Lines 文件（每个文件内一行一个采样点，用统一时间戳体系对齐）：

- `left.jsonl`：左脚传感器原始数据（仅在本次使用了左脚传感器时生成）
- `right.jsonl`：右脚传感器原始数据（仅在本次使用了右脚传感器时生成）
- `gps.jsonl`：GPS 轨迹点
- `battery.jsonl`：电量快照
- `meta.json`：session 元数据，含采样率、绑定位置固定常量"雪靴"、开始/结束时间、本次使用的传感器数量（1 或 2）、实际生成的数据文件名列表、本次使用的校准记录 id 等

校准过程数据存在与 `Sessions/` 平级的 `Calibrations/` 目录下，每次进入校准阶段一个目录，失败的尝试同样保留（决策见 ADR-0012，格式见 system-design.md「持久化策略」）。

## 非功能需求

- **数据完整性优先于实时性**：宁可延迟处理也不能丢数据，这是本阶段最核心的诉求。
- **手套操作**：开始/停止录制等关键操作按钮要足够大，避免需要摘手套精细点击。
- **无网络**：全部功能（连接、录制、存储、回放）不依赖网络。
- **续航**：目标覆盖半天滑雪（约 4 小时），具体数值待现场实测后回填（已有电量记录机制支持测算）。
- **数据可导出**：录制的数据文件需要能被用户直接访问、导出，不依赖 Xcode 手动导出容器；至少支持通过 iOS 系统的 Files App 直接查看 session 数据目录（见 ADR-0004）。
- **低温环境**：不做特别处理，作为已知风险接受。
- **传感器电量显示**：连接、准备录制、录制中显示已连接传感器的电量，低电量时用红色提示；不拦截任何操作。只针对传感器，不含手机电量。显示位置、布局和断线规则见 ADR-0015。
- **权限**：App 启动时按需申请蓝牙、定位权限，遵循 iOS 标准弹窗流程。
- **最低系统版本**：iOS 17，不考虑向下兼容更早版本（自用 App，不需要兼容旧设备）。

## 成功指标

- 连续录制 5 趟以上（每趟 3–10 分钟），蓝牙连接无静默丢数据（断线可被检测并标记，不是无声漏数据）。
- 双传感器场景下，两路数据时间戳同步误差在可接受范围内（初步定为 < 50ms，待现场验证该阈值是否合理；单传感器场景不涉及此项）。
- GPS、电量、IMU 数据能完整落盘，session 结束后可通过时间轴 + 3D 回放正常查看，无数据损坏/解析失败。

## 开放问题

**待现场测试验证（已有数据采集机制支持，等真实滑雪数据回填结论）**
- 实际续航时长。
- 雪场环境（山区、可能信号遮挡）下 GPS 精度和更新频率的实际表现。
- 后台定位对续航的影响，可结合电量数据分析。
- 双传感器时间戳同步误差阈值（初定 < 50ms）是否合理。
- 录制阶段每次 BLE notify 带 2 帧、共用同一个到达时间戳（见 system-design.md「时间戳来源」），对后续分析的影响有多大。

**推迟到后续阶段**
- 转弯分段算法、刃角/对称性等指标计算——需要收集到真实滑雪数据后再设计，明确不在 MVP 范围内。
