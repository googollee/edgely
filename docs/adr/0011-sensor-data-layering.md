# 0011 传感器数据分两层处理：设备适配层重整原始数据，使用方消费整理后的流

## 决策

把传感器数据处理拆成两层：设备适配层按经验和协议说明重整原始数据，输出一条稳定的采样流，不做切片、不保存历史；使用方（校准流程、录制）只消费这条流。

### 第一层：设备适配层

- **输入**：设备原始数据（从 BLE 解析出的实时帧，含加速度、角速度，以及所在数据包的到达时间）。
- **输出**：一条整理后的采样流，每个样本含帧序号、重建时间 `t`、统一单位的加速度（g）和角速度（deg/s）、所在数据包的到达时间（只用于把样本对应到用户点击的时刻和落盘分析，算法不读）。设备协议的细节到这里为止。
- **只重整，不切片**：输出是整条流，窗口切片由使用方按需做。
- **不保存历史**：样本整理出来就交给订阅者，没人订阅时直接丢弃。
- **落盘存原始数据，不存整理后的结果**：规则变了，旧数据可以重新整理。因此使用方落盘时要同时保留到达时间与帧序号。
- **重整逻辑是纯计算，不依赖 CoreBluetooth**：可以用落盘数据直接回放做单元测试。
- **时间轴在本层流式重建**：样本到达时就给出重建时间 `t`，发出之后不再修改，不依赖窗口。重建算法本身不在本决策范围内。
- **设备不一定具备的能力通过可选能力协议暴露**（电量、磁场、欧拉角、回传速率设置等），使用方按需判断，不具备就跳过；设备专有的数据格式不进通用接口。
- **状态仅限重整所需的少量内容**（时间轴估计的状态、帧计数等），不保存样本历史。以后需要回看更多历史的重整规则在本层追加，不影响使用方。
- **以后接入其他设备**：实现同一个设备适配接口即可，校准流程不用改。

### 第二层：使用方

- 校准流程订阅采样流，自己决定怎么缓存：一个校准会话从开始到结束累积全部整理后的样本，结束即丢弃；窗口按两次点击的时刻从会话累积里切出。
- 录制边收边落盘，不需要窗口。录制记录的 `t` 是否也取自这条流，不在本决策范围内。

## 依据

- 需求：[F-002](../prd.md#f-002)。
- 校准时间轴需要按采样序号重建（不直接用 BLE 到达时间），最初的实现把重建放在取窗口的地方：先从固定上限的滚动缓冲里按窗口起点切片，再对这个窗口做拟合。这带来三个问题：
  - 同一个样本在不同窗口里得到不同的 `t`：时间轴在窗口内拟合，窗口一变，估计结果和时间零点都跟着变，重整结果依赖切片方式而不是数据本身。
  - 重整规则只服务校准：录制阶段拿不到同样的重整结果，以后任何新的重整规则（零偏修正、丢帧处理等）都得在两处各写一遍。
  - 缓冲区大小由重整层决定，需求却来自使用方：滚动缓冲的上限是拍出来的数字，与任何使用方的真实需求无关。
- 以后可能接入其他设备，设备协议的细节（帧格式、寄存器、单位）不应泄露到校准流程里。
- 重整所需的回看长度和使用方需要保留的历史是两件事：
  - 重整：所需的历史很短，可以随数据流递推，不需要保存窗口。
  - 使用方：由使用方自己决定。校准会话有上限（四步、每步至多 10 秒，50Hz 下每个传感器约 2000 条，内存可以忽略）；录制边收边落盘，不需要窗口。

## 备选方案

### 单层，每个窗口各自重整（未采纳）

结构最简单。但同一样本在不同窗口里 `t` 不同，重整规则只在校准里生效，设备细节泄露到校准流程。新的重整规则无处可放，也与接入新设备的需求冲突。

### 第一层同时负责窗口切片（未采纳）

使用方拿到的就是现成窗口，调用面最小。但窗口边界是点击事件，属于流程语义，不是数据性质；第一层绑上窗口，就回到"同一样本不同窗口不同 `t`"。违背第一层只重整的原则。

### 用设备片上时钟给第一层校时（未采纳）

片上时钟与采样节拍同源，可以提供比到达时间更好的锚点，并为丢帧提供旁证。但只能逐次轮询快照，要持续占用同一条 BLE 链路，还需要额外的锚点对齐逻辑。时间轴重建不依赖它，已经够用。

## 影响

- 重整规则只写一处，使用方共用同一份整理后的数据。
- 同一样本的 `t` 与窗口无关，重整可以用真实数据离线回放，规则变化可回归。
- 接入新设备只需实现设备适配接口，历史留多久由使用方决定，没有固定上限。
