# 0014 采样时间轴的丢帧修正：适配器流式因果估计

## 决策

设备适配层用 0 秒前瞻的因果算法估计丢帧，实时给出时间；样本发出后 `t` 不再修改，录制文件里的 `t` 就是这个流式结果，不做事后重算。

### 模型

第 i 帧的时间是 `c + T·(i + N)`，`T` 是名义采样周期（不再估计），`N` 是到此为止丢掉的帧数，只增不减，以一个 notify 的帧数为单位（50Hz 为 2 帧）。到达时间只会晚于真实时刻，所以用到达时间减候选时间的 10% 分位数损失（而不是平方误差）选 `N`，使估计贴近到达时间的下包络；`N` 每上跳一个单位付一个惩罚。

周期取名义值：周期偏差带来的漂移会被当成"多丢了几帧"吸收掉，对时间误差几乎没有影响（±150ppm 的周期偏差下，时间误差 p95 仍约 40ms，只是估计的丢帧总数偏离 ±70 帧左右）。

### 适配器：因果估计，前瞻为 0

每个 notify 到达时做一步 Viterbi（候选窗口 129 个状态，最优候选靠近上沿时整体上移），取当前代价最小的候选作 `N`，对已发出的 `N` 取历史最大值以保证 `t` 严格单调，再立即发出该 notify 内各帧的时间。样本发出后 `t` 不再修改。

### 录制

`sample` 记录写流式 `t`，同时保存 `arrivalT`，供事后分析；录制结束不再对文件做任何重写。

### 精度

流式时间轴的相邻间隔绝大多数是 20ms，其余为 40ms 整数倍的丢帧跳变，没有 BLE 到达时间的 30ms 成对重复；`t` 严格单调。相对真实时间的误差 p50 约 80ms，p95 约 160ms，最大约 400ms；相对到达时间无累积漂移。这个精度对实时判断和跨十几秒的统计（踏频、与 GPS 对齐）够用。

## 依据

- 需求：[F-003](../prd.md#f-003)（录制的时间戳）、[F-004](../prd.md#f-004)。
- 此前的时间轴按采样序号重建（第 i 帧的时间是 `i × 周期`，到达时间只用来估计周期）。它的前提是不丢帧：协议没有序号，丢帧无法检测，丢一帧会让之后的时间整体偏移一个周期。
- 真实骑行记录表明这个前提不成立：
  - 丢帧率约 1%–2%，集中在个别时段，局部（30 秒窗口）最多可达约 8%。设备本身是稳定的 50Hz。
  - 每个 notify 恒带 2 帧，丢包按 notify 为单位，所以时间轴上的丢帧表现为 40ms 的整数倍跳变。
  - 均匀时间轴 `i × 周期` 相对 BLE 到达时间会累积出几秒到十几秒的偏差。
  - 到达时间有排队滞后（中位约 60ms，p99 约 376ms）：iOS 在连接事件上交付，堵住后会补发。所以单帧丢失在滞后噪声里分辨不出，能做到的是 ±1–2 帧（20–40ms）的精度。
- 带遗忘的周期估计限幅在名义值 ±2%，追不上局部 8% 的丢帧，周期估计本身还会被丢帧带偏。
- 后续有实时提醒的需求（对姿态、角速度做在线判断），适配器给出的时间轴需要在运动中就可用，不能等整段数据。

## 备选方案

### 保持现状，不修正丢帧（未采纳）

不改代码。但 `t` 相对到达时间有几秒到十几秒的偏差，与 GPS 对齐、跨十几秒的统计（踏频、里程）会受影响，原有的"不丢帧"前提在真实数据上不成立。偏差量级与分析需要的精度相差一个数量级以上。

### 流式估计之外，保存时再用离线动态规划重算（未采纳）

离线可以看全局，精度更高（误差 p95 约 40ms，最大约 200ms）。但录制过程中读到的 `t` 与保存后文件里的不一致；需要保留 `tCausal` 字段、临时文件替换、崩溃恢复，以及一份与适配器同模型的离线实现；重算的内存和耗时随时长增长。流式结果的精度对实时判断和统计分析已经够用，不值得为此付出复杂度和双版本不一致。

### 适配器带前瞻（延迟 1–3 秒）的流式算法（未采纳）

| 前瞻延迟 | p95 | 最大 |
| --- | --- | --- |
| 0 s | 160–200 ms | 400–480 ms |
| 0.5 s | 160–200 ms | 240–280 ms |
| 1.0 s | 120 ms | 200–240 ms |

精度更高。但每个样本要晚 1 秒以上才能发出，对实时提醒不友好；实时提醒看的是短窗口内的信号，用相邻帧的 dt，丢帧只让局部少 20–40ms，累积漂移才是问题，不值得为它付延迟。前瞻延迟可以作为参数以后再引入（例如双传感器对齐需要时）。

### 读设备片上时钟检测丢帧（未采纳）

协议有只读的片上时间寄存器，但需要轮询并占用同一条 BLE 链路，还需要额外的锚点对齐逻辑。本问题用到达时间的下包络已经能处理，暂不引入。若出现更长的丢帧或需要双传感器精确对齐，再评估。

## 影响

- 时间轴相对到达时间无累积漂移，实时路径零延迟。
- 录制中看到的 `t` 与落盘的 `t` 一致，没有重写文件的步骤，也没有崩溃时的中间状态。
- 估计出的丢帧数本身是链路质量指标，可以按时段给出。
- 时间轴的真值只能靠推断：精度只到 ±1–2 帧，`t` 的绝对偏移（到达时间下包络的 0–几十 ms 常量）无法确定。
- 单调性约束让流式估计整体偏晚约 40ms；无丢帧时每 2 分钟凭空多估约 10 帧（0.2 秒）。
- 周期偏差和丢帧在估计里不可区分，估计的丢帧总数不能当作精确值。
- 流式估计偶尔会把相邻的两次丢包合并成一次更大的跳变，没有事后的修正。
- 回传速率固定为 50Hz，一个 notify 的帧数取实测值 2；若以后重新开放其他速率，需要补测一次 notify 带几帧。
- 需要更多真实记录验证（不同手机、不同蓝牙环境、更差的链路），并回填参数（分位点 0.1、上跳惩罚 0.05、候选窗口 129）。
