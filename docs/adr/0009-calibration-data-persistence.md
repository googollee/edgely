# ADR-0009：校准过程数据落盘，失败的尝试同样保留

## 背景（Context）

F2 校准带有一批判定参数，全部是没有真实数据支撑的保守占位值：端点取样的观察长度、姿态积分漂移容差、峰值速度下限、方向一致性下限、后迈校验容差、相对区分度、单步时限。这些值只能靠真实滑雪场景的数据回填。

校准判定所用的数据来自一个纯内存的滚动缓冲区，校准结束即清空；而校准失败的处理是整体重来，面向用户的提示也刻意做得粗粒度（只说校准失败、请重新开始），不细分是哪一项判据没过。这个提示粒度对用户是合理的——现场戴着手套，看懂细分原因也不会让他调整得更好——但如果判定数据不另行保存，**失败现场就不会留下任何可供事后分析的痕迹**。

那样的话，现场测试跑完，遇到用户反复失败最后放弃的情况，手上除了「他说校准老是不过」之外什么都没有：既不知道是哪一项判据在拦，也不知道拦在什么数值上，没有任何依据去调那批占位参数。

## 决策（Decision）

**校准过程的数据落盘保存，成功和失败的尝试一视同仁地保留。**

- **写到独立目录，不写进 session 目录**：每次进入校准阶段建立一个以时间戳命名的目录（`Calibrations/<时间戳>/`），与 `Sessions/` 平级。
- **记录三类内容**：
  1. **每一步每个传感器的原始窗口数据**——就是交给算法判定的那批采样（`TimedSample` 序列：相对时间戳、加速度、角速度），沿用 ADR-0001 的 JSON Lines 格式。
  2. **每一步的判定中间量**——`downStart`/`downEnd`（端点取样的实测值）、姿态积分漂移夹角、峰值速度、方向一致性、后迈校验夹角、窗口时长与采样数，以及这一步的结局（通过，或者是哪一项判据没过）。
  3. **本次校准的结局**——完成还是在第几步被重置、重来了几次、最终判定的左右身份与参考系。
- **失败的尝试必须保留**：用户在同一次校准阶段里重来多次，每一次尝试都独立记录，不覆盖、不合并。
- **不面向用户展示**：这些数据纯粹是留档分析用，UI 上仍然只提示「校准失败，请重新开始」。

## 备选方案（Alternatives Considered）

### 方案 A：校准数据不落盘

- 优点：实现最省，不占存储，校准阶段的数据生命周期最简单（只在内存里存在）。
- 缺点：那批占位参数将没有回填依据。现场只能靠人肉描述「好像第三步老是过不去」，既无法定位是哪一项判据，也无法判断实际数值离阈值有多远。
- 未采纳原因：等于放弃调参的可能性，而这批参数不调准，整个校准的可靠性就是未知数。

### 方案 B：写进 session 目录

- 优点：校准数据天然跟它服务的那趟录制关联在一起，不需要额外的目录层级和关联字段。
- 缺点：session 目录是**开始录制时才创建**的，而校准发生在那之前。这意味着只有「校准成功并且用户随后真的开始录制」这一条路径上的数据才留得下来——**恰恰把最有价值的那部分丢掉了**：用户反复失败、最后放弃、根本没开始录制的那些尝试，才是最需要拿来调阈值的样本。
- 未采纳原因：会系统性地丢失失败样本，与本决策的目的直接冲突。

### 方案 C：只记判定中间量，不记原始波形

- 优点：体积极小，一次校准几百字节。
- 缺点：只有数值没有原始数据，就只能验证「这次的峰值速度是 0.12」，没法回答「如果把某一项判据换一种写法，这段数据还会不会失败」。而调阈值的过程里，经常会发现问题不在阈值本身而在判据的设计——那时候没有原波形就只能重新去现场采一次。
- 未采纳原因：原始数据的体积其实很小（一次校准 5 步、每步最多 4 秒窗口、50Hz、最多 2 个传感器，合计两千条左右），省下这点空间换来的是分析能力的实质性缺失。

### 方案 D（采纳）：独立目录，原始波形与判定中间量都记，失败尝试同样保留

- 优点：失败样本完整留存；既能复算也能直接看数值；与 session 数据解耦，校准的生命周期不依赖录制是否发生。
- 缺点：校准阶段需要一条独立于录制的落盘路径；长期会累积一批小目录。
- 未采纳原因：N/A（此为采纳方案）。

## 后果（Consequences）

- 正面：
  - 那批占位参数第一次有了回填依据，现场测完可以拿真实数据重新跑判据、调阈值。
  - 失败样本完整保留，能回答「用户到底卡在哪一项」这个问题，而不需要在 UI 上把细节暴露给戴着手套的用户。
  - 沿用 ADR-0001 的 JSON Lines 格式，可以直接用 `jq`/pandas 分析，不需要额外的读取工具；目录同样落在 Documents 下，可以通过 Files App 导出（见 ADR-0004）。
- 负面 / 需要承担的代价：
  - 校准阶段多出一条落盘路径：滚动缓冲区本身仍是临时工作区，但交给判定的那些窗口会被复制一份写盘。
  - 每次校准尝试都产生一个目录，反复失败会产生多个。单次体积很小（百 KB 量级），但没有自动清理机制，长期会累积。MVP 阶段不做自动清理，用户可以从 Files App 手动删除；如果现场发现增长过快，再考虑加保留策略。
  - 落盘需要处理写入失败的情况。校准数据是留档分析用的，写失败不阻断校准流程本身——丢一次记录比让用户没法开始滑要好。
- 对后续工作的影响：
  - 现场测试之后，应当拿这批数据重新评估全部占位参数，并把结论回填进 ADR-0007（算法阈值）和 ADR-0008（流程与判定阈值）。
  - ADR-0007 决定不对窗口两端做静止性检测，完全依赖指令文案——如果用户经常在动作未完成时点击确认，落盘的原始窗口末端会看到明显的陀螺仪读数，这是判断要不要重新引入端点检测（见 ADR-0007 方案 G）的直接依据。
  - 成功的那次校准，其目录 id 应当写进随后 session 的 `meta.json`，便于把「这趟数据用的是哪次校准的参考系」关联起来。
  - 参数调完、可靠性验证过之后，可以重新评估是否还需要长期保留这套记录，或者改成只在调试开关打开时记录。
