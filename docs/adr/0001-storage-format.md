# ADR-0001：原始数据使用 JSON Lines，按数据流拆分多文件存储

## 背景（Context）

MVP 需要在滑雪现场（无网络）持续采集多路异步数据流：1~2 路 IMU（取决于本次使用的传感器数量）、GPS、电量快照，各自采样率不同（IMU 可能 25–100Hz，GPS 约 1Hz，电量每分钟一次）。PRD 中已明确"数据完整性优先于实时性"——录制过程中 App 被系统挂起、蓝牙短暂断开、甚至进程被杀，已写入的数据都不能丢失或损坏，因此必须支持安全的增量写入，而不是录制结束时才统一落盘。

## 决策（Decision）

原始数据使用 **JSON Lines** 格式（每行一个独立的 JSON 对象，代表一个采样点）。每次录制（session）对应一个目录，按数据流拆分成多个 `.jsonl` 文件：

- `left.jsonl`：左脚传感器原始数据（仅在本次使用了左脚传感器时生成）
- `right.jsonl`：右脚传感器原始数据（仅在本次使用了右脚传感器时生成）
- `gps.jsonl`：GPS 轨迹点
- `battery.jsonl`：电量快照

外加一个 `meta.json` 存 session 级元数据（采样率、绑定位置、开始/结束时间、本次使用的传感器数量、实际生成的数据文件名列表等）。这个文件是整体覆盖写入（session 开始、结束时各写一次完整内容），不是像 `.jsonl` 文件那样逐行追加。

## 备选方案（Alternatives Considered）

### 方案 A：单一大 JSON 数组文件

- 优点：结构直观，一个文件包含所有数据。
- 缺点：必须维护完整数组结构（开头 `[`、结尾 `]`），追加新采样点需要在结尾插入而不是简单 append；录制中途崩溃容易导致文件缺少收尾括号，整个文件无法解析。
- 未采纳原因：不支持安全的增量写入，直接违反"数据完整性优先"的核心非功能需求。

### 方案 B：SQLite 数据库

- 优点：支持事务保证写入原子性，结构化查询方便，多数据流可以用不同表分开存储。
- 缺点：引入数据库依赖和 schema 管理复杂度；不能直接用文本编辑器/命令行工具查看内容；MVP 阶段目标是"先把数据攒下来，后续再设计分析算法"，不需要 SQL 查询能力。
- 未采纳原因：复杂度相对当前需求过剩。

### 方案 C：CSV，每种数据流一个文件

- 优点：紧凑、通用，Excel/pandas 都能直接读。
- 缺点：不同数据流字段结构差异较大（四元数 4 个数、加速度 3 个数，未来可能还要加字段），CSV 的表头一旦定下不便扩展，schema 演进容易破坏历史文件的可读性。
- 未采纳原因：数据字段大概率会随协议核实、算法设计迭代，JSON Lines 每行独立、字段可扩展性更好。

### 方案 D：二进制自定义格式

- 优点：体积小、读写快。
- 缺点：MVP 阶段字段还在变动，每次改字段都要同步维护解析器；调试时不能直接查看内容。
- 未采纳原因：当前阶段开发速度和可调试性优先于存储效率。

## 后果（Consequences）

- 正面：
  - 增量追加写入是安全的——单行写入失败最多影响最后一行（可简单丢弃/截断处理），不会破坏已经完整写入的历史数据。
  - 人类可读，方便用 `jq`、pandas 等工具直接探索数据、调试问题，不需要额外的读取工具。
  - 不同采样率的数据流分文件存储，避免"一行一个采样点"在混合多路数据时的字段错位问题。
- 负面：
  - 存储空间比二进制格式大（字段名在每行重复存储），高频 IMU 数据长时间录制可能产生较大文件。
  - 大文件逐行解析的性能不如二进制格式或数据库索引查询，未来如果要做大规模历史数据分析/云端同步，可能需要重新设计存储方案。
- 对后续工作的影响：
  - 这是 MVP 阶段的选择，后续如果引入历史对比、云同步等功能，需要重新评估是否迁移到更结构化的存储（如 SQLite），届时应创建新 ADR 并在此处标注取代关系。
