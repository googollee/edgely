# 0001 原始数据使用 JSON Lines，按数据流拆分多文件存储

## 决策

原始数据使用 JSON Lines 格式（每行一个独立的 JSON 对象，代表一个采样点）。每次录制（session）对应一个目录，按数据流拆分成多个 `.jsonl` 文件：

- `left.jsonl`：左脚传感器原始数据（仅在本次使用了左脚传感器时生成）
- `right.jsonl`：右脚传感器原始数据（仅在本次使用了右脚传感器时生成）
- `gps.jsonl`：GPS 轨迹点
- `battery.jsonl`：电量快照

另有 `meta.json` 存 session 级元数据（采样率、绑定位置、开始/结束时间、本次使用的传感器数量、实际生成的数据文件名列表等）。该文件整体覆盖写入（session 开始、结束时各写一次完整内容），不像 `.jsonl` 文件那样逐行追加。

## 依据

- 需求：[F-003](../prd.md#f-003)、[F-004](../prd.md#f-004)、[F-006](../prd.md#f-006)、[F-008](../prd.md#f-008)。
- 现场无网络，需要持续采集多路异步数据流：1~2 路 IMU、GPS、电量快照，采样率各不相同（IMU 25–100Hz，GPS 约 1Hz，电量每分钟一次）。
- 数据完整性优先于实时性：录制中 App 被挂起、蓝牙短暂断开、进程被杀时，已写入的数据不能丢失或损坏，所以必须支持安全的增量写入，而不是结束时统一落盘。
- JSON Lines 单行写入失败最多影响最后一行（可截断丢弃），不破坏已完整写入的历史数据；人类可读，可以直接用 `jq`、pandas 探索数据；不同采样率的数据流分文件存储，避免混合多路数据时字段错位。

## 备选方案

### 单一大 JSON 数组文件（未采纳）

结构直观，但需要维护开头 `[` 和结尾 `]`，追加要在结尾插入；录制中途崩溃会缺少收尾括号，整个文件无法解析。不支持安全的增量写入，违反数据完整性优先的要求。

### SQLite 数据库（未采纳）

事务保证写入原子性，结构化查询方便。但引入数据库依赖和 schema 管理复杂度，不能直接用文本工具查看；MVP 只需要先把数据攒下来，不需要 SQL 查询能力。复杂度相对当前需求过剩。

### CSV，每种数据流一个文件（未采纳）

紧凑、通用。但不同数据流字段结构差异大，表头一旦定下不便扩展，字段演进容易破坏历史文件的可读性。字段大概率会随协议核实、算法设计迭代，JSON Lines 每行独立、可扩展性更好。

### 二进制自定义格式（未采纳）

体积小、读写快。但 MVP 阶段字段仍在变动，每次改字段都要同步维护解析器，调试时不能直接查看内容。当前阶段开发速度和可调试性优先于存储效率。

## 影响

- 增量追加写入安全，可用 `jq`、pandas 直接读取。
- 存储空间比二进制格式大（字段名每行重复），高频 IMU 数据长时间录制可能产生较大文件。
- 大文件逐行解析的性能不如二进制格式或带索引的数据库。如果后续引入历史对比、云同步等功能，需要重新评估存储方案。
