# ADR-0016：设备适配层抽成 AttSensorKit 协议包，具体设备实现按注册接入，缺少实现时 app 仍可编译

## 背景（Context）

ADR-0011 把传感器数据处理拆成"设备适配层"和"使用方"两层，并约定以后接入新设备时实现 `DeviceAdapter` 协议即可。但现在的代码里，这个约定只做到了一半：

- **连接管理和具体设备绑在一起**：扫描、连接、重连由同一个类负责，它直接创建某一种具体适配器，扫描时也只按这一种设备的服务 UUID 过滤。
- **`DeviceAdapter` 协议太窄**：只有 `id`、`onSample`、`resetStream`。录制、电量监控、连接页都需要更多信息（是否就绪、最近一次收到数据的时间、电量、磁场、欧拉角、回传速率设置、时间零点），这些都只能通过具体类型访问，于是界面层、录制层、电量监控层都直接依赖具体适配器类型，有的地方还要用 `as?` 把协议转回具体类型。
- **设备实现无法独立维护**：设备协议的细节（帧格式、寄存器、补偿算法）与 app 的业务代码混在同一个工程里，无法把它们分开维护，也无法在没有它们的情况下构建 app。

后期还会接入其他类型的姿态传感器，需要一种"新设备只增加实现、不改 app"的机制。

## 决策（Decision）

我们决定：**把设备适配层的契约抽成独立的本地 Swift Package `AttSensorKit`（放在 app 仓库内）；具体设备的实现作为可选包，通过注册表接入，app 本身不依赖任何具体设备实现，缺少实现时仍可编译。**

"Att"取 attitude（姿态）之意。

### 1. 依赖方向

```
Edgely（app）  ──▶  AttSensorKit  ◀──  设备实现包（可选）
```

- app 只依赖 `AttSensorKit`，源码里不出现任何具体设备类型。
- 设备实现包也依赖 `AttSensorKit`，在启动时向注册表注册自己的工厂。
- 设备实现包放在项目根目录的 `EdgelyDevices/` 下，被 `.gitignore` 忽略。工程生成脚本检测到该目录存在就把它加入编译，不存在则忽略（见第 5 节）。

### 2. AttSensorKit 提供的内容

- **设备适配器协议 `DeviceAdapter`**：ADR-0011 中约定的 `id`、`onSample`、`resetStream()`，加上所有设备都有的连接状态和时间基准：
  - `isReady`：连接是否就绪（含重连）；
  - `lastRealtimeAt`：最近一次收到实时数据的时间，断线检测只看它；
  - `timeOrigin: Date?`：时间零点。设置后，`DeviceSample.t` 以它为基准（流的第一个样本 `t` = 到达时间 − 零点，之后按重建间隔递增；流每次重开都用重开后第一个样本重新锚定，断线缺口因此保留）；不设时每条流的第一个样本 `t` 为 0。
- **整理后的采样 `DeviceSample`**：`index`（帧在当前流里的序号）、`t`（重建后的时间）、`accel`（g）、`gyro`（deg/s）、`arrival`（所在数据包到达手机的时刻）。`arrival` 是唯一实测的时间，无论 `t` 如何重建都保留，供后期分析使用。
- **可选能力协议**：设备不一定具备的功能，使用方用 `as?` 判断，不具备就跳过：
  - `BatteryReporting`：电量百分比；
  - `MagneticFieldProviding`：磁场读数；
  - `EulerAngleProviding`：设备自带的欧拉角；
  - `OutputRateConfigurable`：回传速率设置。
- **设备适配器工厂 `DeviceAdapterFactory`**：
  - `serviceUUIDs`：这类设备广播的服务 UUID，用于扫描过滤和认领；
  - `makeAdapter(for:)`：为已认领的外设创建适配器。
- **注册表 `DeviceAdapterRegistry`**：保存已注册的工厂，汇总所有工厂的 `serviceUUIDs` 供扫描使用，并按广播里的服务 UUID 认领设备。
- **`MockAdapter`**：仅用于测试和 DEBUG 构建。DEBUG 构建里可以往设备列表加一个模拟设备，让没有真实设备时也能走连接、录制等界面流程；模拟设备只给静止的数据，通不过校准动作的判定。Release 构建不包含。

### 3. 扫描、认领与连接

1. **扫描**：`scanForPeripherals(withServices:)` 使用注册表汇总的 UUID 列表。**列表为空时不启动扫描**（传空数组会变成全量扫描），界面提示"没有可用的设备支持"。
2. **认领**：发现设备时，用广播里的 `CBAdvertisementDataServiceUUIDsKey` 与各工厂的 `serviceUUIDs` 比对，命中的工厂即为该设备的归属工厂，设备才会出现在列表里。多个工厂同时命中时按注册顺序先到先得，暂不设优先级。
3. **连接后确认**：连接后做 `discoverServices`，检查实际发现的服务里是否包含归属工厂声明的 UUID；有才创建适配器，没有就断开并提示"不是支持的设备"。这是注册表的默认行为，工厂不需要实现；需要更严检查的工厂可以覆盖。
4. **连接管理**：扫描、连接、断线自动重连（PRD F1/F4）由通用的设备管理器负责，不认识任何具体协议。适配器在被认领、确认之后接手外设。

### 4. 消费者只依赖协议

app 里的录制、电量监控、连接页、校准等一律改为依赖 `DeviceAdapter` 及能力协议。app 源码中不再出现任何具体设备类型，也不再有从协议转回具体类型的转换。

### 5. 工程生成

- `project.yml` 保持不含设备实现包的基础配置，另有 `project.devices.yml` 只写设备实现包的增量（包依赖和 target 依赖）。
- `scripts/gen_proj.sh` 检测项目根目录下是否存在 `EdgelyDevices/`：存在则合并两份配置生成工程，不存在则只用基础配置。
- `Makefile` 提供 `make proj` 调用该脚本。
- `Edgely.xcodeproj` 与 `Generated/` 不进版本管理，每台机器各自生成。
- `project.devices.yml` 同时设置编译条件 `EDGELY_DEVICES`，app 中的注册代码用 `#if EDGELY_DEVICES` 包起来，设备实现包存在时才参与编译。不用 `canImport`：构建目录里残留的旧模块会让它在没有设备实现包时仍然判断为真，导致链接失败。

### 6. 没有设备实现包时的行为

- app 可以编译、运行。
- 注册表为空，扫描不启动，连接页列表为空并给出提示。
- 因此无法连接真实设备、无法校准、无法录制。DEBUG 构建里的模拟设备用来验证界面和流程。

## 备选方案（Alternatives Considered）

### 方案 A：保持现状，设备实现留在 app 内（不采纳）

- 优点：不需要拆分，改动最小。
- 缺点：app 与设备协议细节无法分开维护；接入新设备要改 app 的多处代码；界面层继续依赖具体类型。
- 未采纳原因：不能满足"设备实现独立于 app 编译"的目标。

### 方案 B：直传适配器——未被认领的设备也能连，把原始字节原样录盘（不采纳）

- 优点：没有设备实现包时 app 仍能录下东西，供以后分析未知协议。
- 缺点：蓝牙没有标准的姿态传感器服务，不认识协议就拿不到加速度和角速度，直传数据无法用于校准和回放；还需要为这种数据另设落盘格式，并让校准、回放界面处理"只有原始数据"的情形。
- 未采纳原因：价值有限，复杂度却很高。改为只显示被认领的设备。

### 方案 C：声明式设备描述文件 + 通用适配器（不采纳）

- 优点：不写代码也能接入帧格式固定的设备，没有设备实现包时 app 也能解析数据。
- 缺点：只能表达固定布局的帧，需要发命令、读寄存器的设备表达不了；需要定义并维护一套描述文件格式；没有描述文件的设备依然无法添加。
- 未采纳原因：复杂度与收益不成比例，当前只需要接入少量设备，直接写适配器更简单。

### 方案 D：按设备名过滤设备（不采纳）

- 优点：用户看到的是设备名，直观。
- 缺点：CoreBluetooth 系统层面只支持按服务 UUID 过滤，按设备名过滤要全量扫描后在 app 里自己筛选；设备名可被用户修改，也可能为空或撞名；各工厂需要提供名字规则，协议更复杂。
- 未采纳原因：UUID 过滤由系统在蓝牙芯片上完成，更省电，规则也更稳定。

### 方案 E：设备实现以源码目录形式并入 app target，不走 Swift Package（不采纳）

- 优点：不需要第三个包，也不需要把协议层独立出来。
- 缺点：设备实现和 app 在同一个模块里编译，边界只靠约定，没有编译器强制，容易再次出现 app 直接引用具体类型。
- 未采纳原因：需要由编译器保证 app 不依赖具体设备。

## 后果（Consequences）

- 正面：
  - app 与设备实现解耦：app 不引用任何具体设备类型，缺少实现包时也能编译。
  - 新增设备只需要新增一个工厂和适配器，不改 app。
  - 能力协议让 UI 能优雅降级：设备没有电量就不显示电量条，没有磁场就不采磁场。
  - `MockAdapter` 让界面和流程在没有真实设备时也能开发和测试。
- 负面 / 需要承担的代价：
  - 没有设备实现包时 app 什么设备都连不上。
  - `AttSensorKit` 的协议成为跨包契约，改动要同步所有设备实现，需要给包打版本标签。
  - **按服务 UUID 过滤要求设备把服务 UUID 放进广播包**。广播包很短（约 31 字节），不广播服务 UUID 的设备（要连上才能看到）会被过滤掉，无法用这套机制接入。接入新设备前需要先验证它是否广播服务 UUID。
  - 重构牵涉面大：界面、录制、电量监控、连接管理以及大部分测试都要改。
  - 设备实现的单元测试随实现包迁走，app 的测试改用 `MockAdapter`。
- 对后续工作的影响：
  - 丢帧修正由适配器流式完成（ADR-0014），app 不再做时间轴重算；落盘的时间字段是 `t`、`arrivalT`、`wallClock`、`frameIndex`。
  - ADR-0011 的分层方向不变，本决策在它的基础上补充注册、识别和包划分；ADR-0011 中"设备专有能力留在具体类型上"的做法，被能力协议取代。
  - 以后若需要后台扫描、设备优先级或更严格的设备确认，可在工厂接口上增量扩展。
