# ADR-0005：F5 姿态渲染——鞋形简化几何体 + 校准对齐 + 加速度计倾斜锚定

| 字段 | 内容 |
| --- | --- |
| 状态 | 已采纳 |
| 日期 | 2026-09-20 |
| 决策者 | Googol Lee |
| 关联 PRD | docs/prd/mvp.md（F2、F5） |

## 背景（Context）

F5 用传感器原始欧拉角（Angle 字段）直接驱动一个对称方块的朝向（`Pose3DView`，渲染引擎见 ADR-0002）。这带来两个问题：

1. 对称方块没有任何视觉线索表明"哪一面是脚尖、哪一面是鞋底"，观察者无法把渲染结果和真实的鞋对应起来。
2. 直接用 Angle 字段驱动渲染，无法保证"下"方向在回放中始终朝下——WT901 的欧拉角旋转顺序/正负号约定是否和 SceneKit 的 `eulerAngles` 约定一致，目前尚未验证（见硬件协议参考文档的开放问题）。

F2 校准阶段算出的 `SensorOrientationFrame`（`down`/`front`/`left`，在传感器原始坐标系下表达）目前只落盘到 `meta.json`，回放没有使用它。

## 决策（Decision）

1. **几何体**：把渲染用的对称方块换成一个简化的、不对称的鞋形组合形状（如长方体主体 + 一端加锥体/楔形表示脚尖，鞋底面用不同颜色区分），在固定的模型局部坐标系里预先定义好"脚尖方向"和"鞋底方向"。仍然是简化几何体，不是精细雪靴/雪板模型。
2. **校准对齐（常量，session 内计算一次）**：用 F2 算出的 `SensorOrientationFrame`（`front`/`down`/`left`）计算"模型局部坐标系 → 传感器坐标系"的对齐旋转，把鞋形模型的朝向和真实鞋的朝向对齐。
3. **实时倾斜（每个回放时间点计算）**：不使用 Angle 字段，改用**原始加速度计读数**，计算"相对校准时刻的重力方向，当前时刻转了多少"（最短路径旋转），叠加在对齐旋转之上，驱动模型的实时姿态。

## 备选方案（Alternatives Considered）

### 方案 A：继续用对称方块/箭头，不做鞋形

- 优点：实现成本最低，已经是当前状态。
- 缺点：无法解决"看不出模型朝向和真实鞋对应关系"的问题。
- 未采纳原因：不满足这次要解决的核心问题。

### 方案 B：用 Angle 字段（AHRS 融合姿态角）驱动实时姿态，而不是加速度计

- 优点：Angle 字段本身是传感器内部融合好的姿态角，理论上包含完整的三轴姿态（含偏航），信息量比只用加速度计更完整。
- 缺点：依赖尚未验证的欧拉角旋转顺序/正负号约定，用错约定会导致渲染出的姿态方向错误，且不容易一眼看出错在哪。
- 未采纳原因：在约定验证清楚之前贸然使用，风险高于收益；加速度计的换算公式已经核实、没有歧义，更适合现阶段使用。

### 方案 C：自己用陀螺仪角速度积分重建完整姿态

- 优点：能得到包含偏航的完整姿态，不依赖 Angle 字段的欧拉角约定。
- 缺点：需要实现一套传感器融合算法（陀螺仪积分 + 加速度计校正才能避免长时间漂移），复杂度和工作量明显高于当前阶段其他方案。
- 未采纳原因：MVP 阶段这个复杂度不划算，属于"分析算法"范畴，PRD 已明确推迟到后续阶段（见非目标）。

## 后果（Consequences）

- 正面：
  - 观察者能直观看出模型的脚尖/鞋底朝向，能把渲染结果和真实的鞋对应起来。
  - 下方向始终锚定在真实重力方向，不依赖尚未验证的欧拉角约定。
  - 使用的是已核实、无歧义的加速度计原始数据（见硬件协议参考文档），不引入新的不确定性。
  - F2 校准算出的参考系第一次被实际使用，而不是只落盘。
- 负面：
  - 加速度计只能测"倾斜"（俯仰+横滚两个自由度），测不出绕重力轴的偏航——渲染出的姿态不含偏航信息，滑雪时脚绕纵轴的转向动作不会体现在模型转动上。这是方案的已知局限，不是实现缺陷。
- 对后续工作的影响：
  - 如果后续要还原包含偏航的完整姿态，需要先验证 WT901 欧拉角约定（硬件协议参考文档中的开放问题），再评估改用 Angle 字段（方案 B）或做完整传感器融合（方案 C），届时应创建新 ADR 并在此处标注取代关系。
