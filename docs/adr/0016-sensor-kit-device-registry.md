# 0016 设备适配层抽成 AttSensorKit 协议包，具体设备实现按注册接入，缺少实现时 app 仍可编译

## 决策

把设备适配层的契约抽成独立的本地 Swift Package `AttSensorKit`（放在 app 仓库内）；具体设备的实现作为可选包，通过注册表接入，app 本身不依赖任何具体设备实现，缺少实现时仍可编译。"Att"取 attitude（姿态）之意。

### 1. 依赖方向

```
Edgely（app）  ──▶  AttSensorKit  ◀──  设备实现包（可选）
```

- app 只依赖 `AttSensorKit`，源码里不出现任何具体设备类型。
- 设备实现包也依赖 `AttSensorKit`，在启动时向注册表注册自己的工厂。
- 设备实现包放在项目根目录的 `EdgelyDevices/` 下，被 `.gitignore` 忽略。工程生成脚本检测到该目录存在就把它加入编译，不存在则忽略。

### 2. AttSensorKit 提供的内容

- 设备适配器协议，以及它输出的整理后的采样；
- 设备不一定具备的可选能力协议：电量、磁场、设备自带的欧拉角、回传速率设置，使用方用 `as?` 判断，不具备就跳过；
- 设备适配器工厂（声明服务 UUID、为已认领的外设创建适配器）和注册表（汇总服务 UUID 供扫描使用，并按广播里的服务 UUID 认领设备）；
- 通用的设备管理器（扫描、认领、连接确认、断线重连）；
- 仅用于测试和 DEBUG 构建的 `MockAdapter`：DEBUG 构建里可以往设备列表加一个模拟设备，让没有真实设备时也能走连接、录制等界面流程；模拟设备只给静止的数据，通不过校准动作的判定。Release 构建不包含。

接口细节见[参考文档](../reference/att-sensor-kit-protocol.md)。

### 3. 扫描、认领与连接

1. **扫描**：按注册表汇总的服务 UUID 列表扫描。列表为空时不启动扫描（传空数组会变成全量扫描），界面提示"没有可用的设备支持"。
2. **认领**：发现设备时，用广播里的服务 UUID 与各工厂声明的 UUID 比对，命中的工厂即为该设备的归属工厂，设备才会出现在列表里。多个工厂同时命中时按注册顺序先到先得，暂不设优先级。
3. **连接后确认**：连接后做服务发现，检查实际发现的服务里是否包含归属工厂声明的 UUID；有才创建适配器，没有就断开并提示"不是支持的设备"。这是注册表的默认行为，需要更严检查的工厂可以覆盖。
4. **连接管理**：扫描、连接、断线自动重连（[F-001](../prd.md#f-001)、[F-004](../prd.md#f-004)）由通用的设备管理器负责，不认识任何具体协议。适配器在被认领、确认之后接手外设。

### 4. 消费者只依赖协议

app 里的录制、电量监控、连接页、校准等一律依赖设备适配器协议及能力协议。app 源码中不出现任何具体设备类型，也不做从协议转回具体类型的转换。

### 5. 工程生成

- 基础工程配置不含设备实现包；设备实现包的包依赖和 target 依赖写在单独的增量配置里。
- 生成脚本检测项目根目录下是否存在 `EdgelyDevices/`：存在则合并两份配置，不存在则只用基础配置。
- 工程文件和生成物不进版本管理，每台机器各自生成。
- 增量配置同时设置编译条件 `EDGELY_DEVICES`，app 中的注册代码用 `#if EDGELY_DEVICES` 包起来，设备实现包存在时才参与编译。不用 `canImport`：构建目录里残留的旧模块会让它在没有设备实现包时仍然判断为真，导致链接失败。

### 6. 没有设备实现包时的行为

- app 可以编译、运行。
- 注册表为空，扫描不启动，连接页列表为空并给出提示。
- 因此无法连接真实设备、无法校准、无法录制。DEBUG 构建里的模拟设备用来验证界面和流程。

## 依据

- 需求：[F-001](../prd.md#f-001)。
- 此前传感器数据处理已拆成"设备适配层"和"使用方"两层，并约定接入新设备时实现适配器协议即可，但代码里这个约定只做到了一半：
  - 连接管理和具体设备绑在一起：扫描、连接、重连由同一个类负责，它直接创建某一种具体适配器，扫描时也只按这一种设备的服务 UUID 过滤。
  - 适配器协议太窄：只有 `id`、`onSample`、`resetStream`。录制、电量监控、连接页都需要更多信息（是否就绪、最近一次收到数据的时间、电量、磁场、欧拉角、回传速率设置、时间零点），这些只能通过具体类型访问，于是界面层、录制层、电量监控层都直接依赖具体适配器类型，有的地方还要用 `as?` 把协议转回具体类型。
  - 设备实现无法独立维护：设备协议的细节（帧格式、寄存器、补偿算法）与 app 的业务代码混在同一个工程里，无法分开维护，也无法在没有它们的情况下构建 app。
- 后期还会接入其他类型的姿态传感器，需要一种"新设备只增加实现、不改 app"的机制。
- 蓝牙没有标准的姿态传感器服务，按服务 UUID 过滤由系统在蓝牙芯片上完成，更省电，规则也更稳定。

## 备选方案

### 保持现状，设备实现留在 app 内（未采纳）

不需要拆分，改动最小。但 app 与设备协议细节无法分开维护，接入新设备要改 app 的多处代码，界面层继续依赖具体类型。不能满足"设备实现独立于 app 编译"的目标。

### 直传适配器：未被认领的设备也能连，把原始字节原样录盘（未采纳）

没有设备实现包时 app 仍能录下东西，供以后分析未知协议。但蓝牙没有标准的姿态传感器服务，不认识协议就拿不到加速度和角速度，直传数据无法用于校准和回放；还需要为这种数据另设落盘格式，并让校准、回放界面处理"只有原始数据"的情形。价值有限，复杂度很高，所以只显示被认领的设备。

### 声明式设备描述文件 + 通用适配器（未采纳）

不写代码也能接入帧格式固定的设备，没有设备实现包时 app 也能解析数据。但只能表达固定布局的帧，需要发命令、读寄存器的设备表达不了；需要定义并维护一套描述文件格式；没有描述文件的设备依然无法添加。当前只需要接入少量设备，直接写适配器更简单。

### 按设备名过滤设备（未采纳）

用户看到的是设备名，直观。但 CoreBluetooth 系统层面只支持按服务 UUID 过滤，按设备名过滤要全量扫描后在 app 里自己筛选；设备名可被用户修改，也可能为空或撞名；各工厂需要提供名字规则，协议更复杂。

### 设备实现以源码目录形式并入 app target，不走 Swift Package（未采纳）

不需要第三个包，也不需要把协议层独立出来。但设备实现和 app 在同一个模块里编译，边界只靠约定，没有编译器强制，容易再次出现 app 直接引用具体类型。需要由编译器保证 app 不依赖具体设备。

## 影响

- app 与设备实现解耦：app 不引用任何具体设备类型，缺少实现包时也能编译。
- 新增设备只需要新增一个工厂和适配器，不改 app。
- 能力协议让界面能优雅降级：设备没有电量就不显示电量，没有磁场就不采磁场。
- `MockAdapter` 让界面和流程在没有真实设备时也能开发和测试。
- 没有设备实现包时 app 什么设备都连不上。
- `AttSensorKit` 的协议成为跨包契约，改动要同步所有设备实现，需要给包打版本标签。
- 按服务 UUID 过滤要求设备把服务 UUID 放进广播包。广播包很短（约 31 字节），不广播服务 UUID 的设备（要连上才能看到）会被过滤掉，无法用这套机制接入。接入新设备前需要先验证它是否广播服务 UUID。
- 重构牵涉面大：界面、录制、电量监控、连接管理以及大部分测试都要改。设备实现的单元测试随实现包迁走，app 的测试改用 `MockAdapter`。
- 以后若需要后台扫描、设备优先级或更严格的设备确认，可在工厂接口上增量扩展。
